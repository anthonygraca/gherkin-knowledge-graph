# AS-07 — Honest provider availability and proposal provenance

**Issue:** [#29](https://github.com/anthonygraca/gherkin-knowledge-graph/issues/29) · **Parent:** F-07
[#13] · **Milestone:** M3 · **Owner:** C; A reviews provider semantics, B reviews problem shapes.
**Canonical criteria:** [AS-07.feature](AS-07.feature) (7 scenarios, SCN-3101…SCN-3107).
**Status:** specification APPROVED (`docs/reviews/AS-07-spec-review-3.md`, round 3); implementation
complete. Independent acceptance review and merge pending. Depends on AS-06 for the proposal and
workspace presentation.

## Scope

Distinguish unregistered provider (400), registered-but-unavailable provider (typed 503), and a valid
empty result (200 with provenance). Show provider/model/index provenance for every proposal
presentation; label snapshot bindings as CTA bindings, not server index revisions; show missing
historical provenance as “not recorded”; document fake as the default offline path.

## Non-goals

Automatic provider fallback; model installation; provider health as assurance findings; acceptance
decisions; live inference or retrieval-quality claims.

## Normative contract notes

These notes resolve specification-review findings AS07-SPEC-R1…R5.

### Problem extensions

`ProblemDetails` gains two optional extension members:

|Member|Type|Presence|
|---|---|---|
|`failed_provider`|string|Required on `provider-not-registered`; present when a registered discovery provider cannot execute.|
|`registered_providers`|list[string]|Required on `provider-not-registered`; the effective registry, including enabled optional providers.|

The extension members are additive to every problem document; existing problem shapes remain valid.
`registered_providers` comes from `ProviderRegistry.registered`, never a hand-maintained copy.

### Provider outcomes

|Outcome|HTTP|Code|Body/behaviour|
|---|---|---|---|
|Unknown provider|400|`provider-not-registered`|`failed_provider` = requested name; `registered_providers` = effective list.|
|Registered provider cannot execute|503|`provider-unavailable`|`failed_provider` named; no candidates; no fallback; no finding.|
|Successful empty result|200|—|`DiscoveryResponse` with `candidates: []`, retaining provider/model/index.|
|Successful candidates|200|—|Candidates carry provider/model/index per candidate and in the response envelope.|

Provider exceptions are caught at the discovery boundary, logged, and mapped to
`provider-unavailable`; a provider failure is never converted into an assurance finding, an accepted
link, or an empty success. The default provider remains `fake`; no code path silently substitutes it
for a failed configured provider. A CocoIndex-specific error on the code-retrieval surface keeps its
existing mapping; on `/api/discovery` the provider boundary reports `provider-unavailable`.

### Provider catalogue

`GET /api/discovery/providers` (additive, read-only) returns:

```json
{"schema_version": "0.7.0", "default": "fake",
 "providers": [{"name": "fake", "kind": "fixture", "default": true},
               {"name": "cocoindex", "kind": "model", "default": false}]}
```

`kind` is registry metadata (`fixture` or `model`), not a guess from the provider name. The UI uses
it to choose the “fixture-generated” versus “model-backed” label. Optional providers absent from the
effective registry are not listed.

**Historical labels are independent of current availability.** Presentation of a persisted proposal
uses a versioned provider-kind table (`fake` = `fixture`, `cocoindex` = `model`) that is not the
effective registry, so disabling CocoIndex does not erase the meaning of recorded provenance. A
provider absent from both the table and the registry is labelled “provider kind not recorded”; its
recorded name, model version, and index value are still displayed. The index value is labelled a
**CTA snapshot binding** when the historical kind is `model`; when the kind is unknown, the panel
shows the recorded value without asserting a binding/revision meaning. Current availability is shown
separately (“provider unavailable”) and never rewrites the historical provenance.

### Provenance presentation

Covered surfaces: transient discovery candidates, persisted proposals (pending and decided), proposal
details, review history, and hybrid-answer candidates wherever the dashboard renders them. Every
surface shows:

* `provider` (the discovery provider that produced the proposal);
* `model_version` (or “not recorded” when the field is absent or null);
* index identity: for fixture/model candidates, the recorded `index_revision`; for CocoIndex, the
  CTA `index_binding` labelled explicitly as a **CTA snapshot binding**, never as a server-reported
  index revision.

Fixture-generated proposals are labelled from the provider catalogue (`kind: fixture`), not from a
name comparison. Model-backed proposals are distinguishable by `kind: model` and the snapshot-binding
label. A proposal is never labelled accepted unless its review state is accepted; provenance labels do
not confer acceptance. Missing values are rendered as “not recorded” and are never replaced by the
current configuration.

For a legacy proposal without a capture snapshot, provenance comes from `link.provenance`; missing
keys render as “not recorded”. For a decided legacy proposal, the durable decision snapshot is the
source. The dashboard does not currently render hybrid-answer candidates; when an answer view is
added, it must use the same provenance component. The API answer response already carries candidate
provenance and is covered by the contract tests.

### UI states

The candidate panel is bound to the selected requirement and baseline:

* **Unregistered**: displays “provider unavailable”, the `failed_provider` name, and the
  `registered_providers` list; `fake` remains selectable. It never shows candidates from a previous
  provider as current results.
* **Registered failure**: displays “provider failed”, the `failed_provider` name, and that the
  selected provider is unavailable; it does not display an empty-success state and does not
  automatically switch to `fake`.
* **Empty success**: displays “0 candidates” with the retained provider/model/index provenance.
* **Success**: lists candidates with rank, score, and provenance.
* In every state the accepted thread, accepted links, and evidence remain readable.

### Verification boundary

The timeout and recorded-response cases replace only the provider's external transport. The real
provider adapter, `POST /api/discovery`, response/problem mapping, and dashboard consumption are
exercised. API responses are not stubbed for the browser scenario; the UI server receives a
provider registry whose provider uses a deterministic transport. These checks establish
adapter/API/UI behaviour, not live inference or retrieval quality.

### Fake mode documentation

`docs/development-lifecycle.md` and the README state that `fake` discovery is the default offline
development path; the documented invocation requires no model, network, or vector service. This is
verified by inspection as a documentation deliverable.

## Verification plan

Deterministic provider transports plus real API problem documents; component/browser tests for panel
states and provenance labels; no live model required. SCN-3105 tests presentation of the adapter path,
not real inference. The existing `fake` provider remains the default in every test and CI job.
