## Outcome

A scenario can request source/test candidates for its exact baseline. CocoIndex Code supplies
non-authoritative hits; CTA maps them to canonical `CODE-`/`TEST-` artifacts with path, line range,
revision, content hash, retrieval method, model identity, and a CTA-computed snapshot binding.
Unresolved hits and unavailable providers are explicit. Nothing is accepted or verified.

## Scope and non-goals

* Reuses `CocoIndexSearchClient`/`StdioMcpTransport`; no second transport or loosened bounds.
* Adds a deterministic lexical comparator over the same snapshot and eligible files.
* Adds `POST /api/retrieval/code` (additive) and a `cocoindex` `CandidateDiscovery` provider when
  the project is explicitly configured.
* No GraphRAG, chat answers, second framework/index, M2 policy change, or claim that CocoIndex
  indexes Gherkin semantically.
* Does not close AI-02 (#31), AI-03 (#32), AI-04 (#34), AI-05 (#35), or AI-06 (#56).

## Design decisions

* **Snapshot binding, not index identity.** CocoIndex 0.2.43 reports no index revision over MCP.
  `index_binding` is `snapshot:sha256:<digest>` over repository, commit, eligible paths, and their
  authoritative content hashes. It is labelled a binding, never a server index revision.
* **Mapping by authoritative path.** A hit resolves only if its path is a source/test artifact at
  the requested commit and the committed blob hash equals the artifact hash. Otherwise it is an
  explicit unresolved result.
* **Raw score preserved.** `raw_score` is the method's report; `score` is clamped to the existing
  candidate contract's 0..1 range and is not a probability.
* **No mutation.** The provider/service only reads.
