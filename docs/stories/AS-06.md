# AS-06 — Human decisions on version-bound proposals

**Issue:** [#28](https://github.com/anthonygraca/gherkin-knowledge-graph/issues/28) · **Parent:** F-07
[#13] · **Milestone:** M3 · **Owner:** C; B reviews the journal/domain, A reviews provenance.
**Canonical criteria:** [AS-06.feature](AS-06.feature) (29 scenarios, SCN-3001…SCN-3029).
**Status:** specification APPROVED (`docs/reviews/AS-06-spec-review-5.md`, round 5); implementation
complete. Independent acceptance review and merge pending. Owner dispositions are recorded in
[ADR 0012](../adr/0012-closeout-scope-decisions.md) §1.

## Scope

Explicit capture of a discovery candidate as a proposed link; append-only accept/reject decisions with
server-assigned operator, UTC time, reason, proposal snapshot, baseline and endpoint hashes; a review
workspace projection over immutable baselines; a minimal review UI/history.

## Non-goals

Authentication service or multi-user roles; reversal/revocation; automatic acceptance; evidence or
finding mutation; Git writes; running assurance on acceptance; re-capturing after a terminal
decision (reopening requires a separately reviewed change).

## Normative contract notes

These notes resolve the specification-review ambiguities (AS06-SPEC-R1…R9). They are part of the
frozen contract; implementation must match them and `docs/domain-contracts.md`.

### Baseline selection

* Review and capture mutations **require** an explicit `baseline` field in the JSON body. It accepts
  a tag or a full/abbreviated commit SHA, resolved by the repository port. Omission is
  `422 request-validation`; an unresolvable value is `404 baseline-not-found`. There is no implicit
  "latest" for mutations. Workspace reads use the existing `?baseline=` query; omission means the
  latest tagged baseline (read-only convenience, consistent with other reads).
* A baseline response field is the canonical tag when the revision is tagged; otherwise the
  resolved commit SHA. The decision always records `baseline` (display identity) and
  `baseline_commit` (resolved SHA).
* A decision applies in a workspace at baseline *B* when *B* resolves to the decision's
  `baseline_commit`, **or** both endpoint content hashes at *B* equal the decision's recorded
  endpoint hashes. Content equality — never commit equality — decides applicability. This makes an
  evidence-only commit reviewable without treating the different SHA as a source change.

Three separate questions are answered separately; conflating them is what made stale decisions
look like missing proposals:

1. **Addressability (can a review request name this proposal?).** A captured proposal is addressable
   by `link_id` at every resolved baseline. A baseline proposal is addressable when the selected
   baseline declares it in `proposed_links` (fixture proposals are declared at both baselines). A
   link id that is neither captured in the journal nor declared as proposed at the selected
   baseline is `404 proposal-not-found`. Addressability is deliberately independent of freshness.
2. **Freshness (may this decision be recorded at the selected baseline?).** Compare the selected
   baseline's two endpoint hashes with the proposal snapshot hashes. Any absence or difference is
   `409 proposal-stale`; equal hashes permit the decision even across different commits
   (SCN-3018). A captured proposal that is stale at baseline-b is still addressable there, so
   SCN-3009 observes `409 proposal-stale`, not `404`.
3. **Pending-queue visibility (is this proposal current here?).** A proposal is listed as pending at
   baseline *B* only when no terminal decision applies at *B* and it is current at *B*: a captured
   proposal is current when *B* is the capture commit or both endpoint hashes equal the snapshot;
   a baseline proposal is current when *B* declares it. A stale captured proposal is addressable
   but not listed as pending; the review request still returns `409 proposal-stale`.

### Proposal snapshot

A `ProposalSnapshot` contains:

|Field|Meaning|
|---|---|
|`snapshot_digest`|`sha256:<hex>` over the canonical JSON (sorted keys, compact separators) of `source_id`, `target_id`, `relation_type`, `baseline`, `baseline_commit`, `source_content_hash`, `target_content_hash`, `provider`, `model_version`, `index_revision`. `score` and `rationale` are presentation metadata and are excluded.|
|`source_id`, `target_id`, `relation_type`|The proposed relationship.|
|`baseline`, `baseline_commit`|The selected display baseline and resolved commit.|
|`source_content_hash`, `target_content_hash`|Authoritative CTA artifact content hashes at that commit, verified against the submitted values.|
|`provider`, `model_version`, `index_revision`|Reported discovery provenance. Never authenticated as model output; absent values stay null.|
|`captured_at`|Server-assigned UTC timestamp. Not part of the digest.|

**Legacy binding.** An imported proposal that has no capture snapshot (fixture `LNK-007`) acquires
one at the first decision: the server constructs the snapshot from the stored link and provenance,
reads both endpoint hashes at the explicitly selected baseline, and durably records that snapshot
with the decision. No fixture file changes and no separate capture action is required. A later
decision for the same link is refused; the legacy snapshot is never rebuilt.

**Pending representation.** A workspace proposal record is
`{link: TraceLink, snapshot: ProposalSnapshot | null, binding: "captured" | "legacy"}`. A legacy
proposal that has not yet been decided has `snapshot: null`, `binding: "legacy"`, and provenance
read from `link.provenance` (`discovery_provider`, `model_version`, `index_revision`, `score`);
missing values are displayed as “not recorded”, never filled from current configuration. Once a
legacy decision is recorded, the pending record is replaced by the decision event carrying the
durable snapshot. Captured proposals always carry a snapshot.

### Capture surface

`POST /api/link-proposals` (loopback/origin guarded):

```json
{
  "source_id": "SCN-002", "target_id": "CODE-001",
  "relation_type": "implemented_by", "baseline": "baseline-a",
  "source_content_hash": "sha256:…", "target_content_hash": "sha256:…",
  "provider": "fake", "model_version": "fake-fixture-v1",
  "index_revision": "sha256:…", "score": 0.71, "rationale": "…"
}
```

* `201` with `{schema_version, link, snapshot, review_revision, created: true}` on a new capture.
* `200` with the existing `{link, snapshot, review_revision, created: false}` for an identical
  snapshot (same digest) that is still pending. No second capture event is appended.
* `422 proposal-invalid` for an unknown endpoint or a relation direction that contradicts
  `RELATION_DIRECTION`; `409 proposal-stale` when a submitted hash disagrees with the authoritative
  artifact at the selected commit.
* `409 proposal-conflict` when the same `(source_id, target_id, relation_type, baseline)` triple
  already has a pending proposal with a different snapshot digest.
* `409 review-conflict` when that triple already has a terminal decision.
* No validation or conflict failure appends an event or publishes a proposal. Persistence failures
  follow the journal durability rules: a confirmed rollback returns `503` with
  `durability: "not_committed"` and publishes nothing; an unconfirmed rollback returns `503` with
  `durability: "indeterminate"` and publishes nothing to the live projection, while a complete
  committed pair may reappear as a pending capture after restart. A capture never reappears as an
  accepted link.
* The link id is the next free `LNK-nnn` across baseline links and the journal. Capture never writes
  the fixture repository, accepted links, evidence, or findings.

### Decision surface

`POST /api/links/{link_id}/review` (loopback/origin guarded; response remains a `TraceLink`):

```json
{"decision": "accept" | "reject", "reviewer_id": "rv-ana",
 "baseline": "baseline-a", "reason": "…"}
```

Precedence, fixed so each failure has one observable code:

1. Unset configured operator → `503 review-identity-unavailable`.
2. `reviewer_id` different from the configured operator → `403 review-identity-mismatch`.
3. Missing/invalid `decision` or `baseline` → `422 request-validation`.
4. Link id is neither a captured proposal nor declared as proposed at the selected baseline →
   `404 proposal-not-found`. A known proposal that is stale at the selected baseline is **not**
   filtered out here; freshness is step 7.
5. Reject with the `reason` field absent or JSON `null` → `422 request-validation`; reject with an
   empty or whitespace-only reason → `422 review-reason-required`.
6. A terminal decision already exists for the link → `409 review-conflict`.
7. Either endpoint is absent at the selected baseline, or its content hash differs from the snapshot
   → `409 proposal-stale`.
8. Journal append/fsync failure → `503 review-storage-unavailable`; no projection update. The
   problem carries `durability: "not_committed"` when the append was rolled back to the prior
   committed length, or `durability: "indeterminate"` when rollback could not be confirmed. A
   successful response is never returned on either path.

A successful decision returns `200` with the link in `accepted` or `rejected` state. Acceptance
never runs assurance, rewrites findings, changes evidence, or assigns a verification verdict.
Concurrent terminal decisions are serialized by one journal lock: exactly one succeeds and one
`review_conflict` event is *not* appended for the loser; exactly one terminal decision pair exists.

### Journal

Application-owned NDJSON, opened append-only and fsynced before the in-memory projection is
published. Path comes from `CTA_REVIEW_JOURNAL`; the default is
`<repo_root>/.cta/review-journal.ndjson`. Startup rejects a path inside `fixtures/` or inside the
evaluated fixture repository.

Each committed event is **two lines**: a payload line containing the event and its
`record_digest` (`sha256:<hex>` over the canonical JSON of the event object), immediately followed
by a commit line `{"commit": "<same digest>"}`. The payload line is fsynced before the commit line
is written; the commit line is then fsynced. Only a payload line followed immediately by a matching
commit line is committed. Replay reconstructs the projection from committed pairs only.

An event carries: `review_revision` (1-based committed-event position), `event`
(`proposal_captured` | `decision_recorded`), `recorded_at` (server UTC), `operator`, `baseline`,
`baseline_commit`, the full `link`, the full `snapshot`, `decision` (null for capture), and `reason`.

Failure and tail rules:

* Before appending, the journal records its committed length. If any payload/commit write or fsync
  fails, it attempts `ftruncate` back to that length and fsyncs again. If that succeeds, the record
  is **not committed**: the response is `503 review-storage-unavailable` with
  `durability: "not_committed"`, the in-memory projection is unchanged, and restart replays only
  the prior committed prefix. Truncating an uncommitted tail never rewrites committed bytes.
* If the rollback truncate/fsync cannot be confirmed, the outcome is **indeterminate**: the response
  is `503 review-storage-unavailable` with `durability: "indeterminate"`, the application never
  reports success, and the journal is marked poisoned. Further mutations are refused with the same
  code until an operator reconciles the file. On restart, replay accepts either no decision or one
  complete committed pair; a partial or malformed record is never replayed. If the complete pair
  survived, the decision appears in history with its durable snapshot and no response ever claimed
  it had succeeded.
* A crash may leave an incomplete or uncommitted tail without an application-level rollback. On
  restart such a tail is **not replayed**. While it exists, every subsequent mutation is refused
  with `503 review-storage-unavailable`; the application never appends after the tail (which would
  turn it into an interior malformed record). The documented repair is operator truncation to the
  last commit-line newline. Reads remain available and replay the committed prefix.
* A malformed *committed* pair (bad JSON or digest mismatch before the tail) is a storage failure
  (`503`), never silently skipped.
* Restart never rewrites existing committed bytes. Append-only application behavior is not a claim
  of tamper-resistant storage.

### Workspace reads

|Endpoint|Response|
|---|---|
|`GET /api/workspace/threads/{artifact_id}?baseline=`|`WorkspaceThreadResponse`: the existing thread fields plus `review_revision`; decisions are projected over immutable baseline facts. Accepted links contain only accepted links; rejected links are absent from both arrays.|
|`GET /api/workspace/proposals?baseline=`|`WorkspaceProposalsResponse`: `{schema_version, baseline, review_revision, proposals: [ProposalRecord]}` — the pending queue for that baseline after freshness and terminal decisions. `ProposalRecord = {link, snapshot: ProposalSnapshot | null, binding: "captured" | "legacy"}`.|
|`GET /api/workspace/history?baseline=`|`WorkspaceHistoryResponse`: `{schema_version, baseline, review_revision, events}` — capture and decision events applicable to that baseline; each event carries its durable snapshot and original provenance.|
|`GET /api/review/config`|`{schema_version, enabled, operator, loopback_only: true}`. `operator` is null when unset.|

Baseline endpoints (`/api/threads`, `/api/findings`, `/api/artifacts`, `/api/links`) are unchanged
by decisions; the workspace is an explicit projection. A workspace thread follows both accepted
and proposed links to assemble the review neighbourhood, then partitions the result: `accepted_links`
contains only accepted links and `proposed_links` only proposals. A consumer walking only
`accepted_links` still cannot traverse a branch that is merely proposed.

### Local write boundary

Review and capture mutations are accepted only when the socket peer is loopback
(`127.0.0.1`, `::1`, or the in-process ASGI test transport) and, when an `Origin` header is present,
its host is loopback (`127.0.0.1`, `localhost`, `[::1]`). A missing `Origin` is allowed for local
CLI/non-browser clients. Non-loopback peer → `403 review-loopback-required`; disallowed browser
origin → `403 review-origin-forbidden`. No authentication service is introduced. Residual risk:
any process with access to the local account can act as the operator.

### UI

The dashboard's review workspace lists pending proposals for the selected requirement with
provider, model version, index revision, and a fixture/model-backed label; accept and reject
controls (reject requires a nonblank reason); and the decision history. It uses the workspace
endpoints above.

* A successful rejection removes the proposal from accepted links and the pending queue and shows
  the rejection, reason, operator, and server timestamp in history.
* A refused write displays the typed problem code and detail as an error. The UI never marks the
  proposal accepted optimistically; a subsequent workspace refresh displays the server's actual
  projection (including a decision recorded by another local process).
* Missing provenance renders as “not recorded”; the UI never substitutes current configuration.
* A decision refresh re-reads the workspace projection; the UI never mutates local state
  optimistically.

acceptances, and rejections; concurrent writes; conflicting and duplicate captures; invalid
direction/hash; stale snapshots; evidence-only revisions; uncommitted-tail refusal; loopback/origin

scenarios SCN-3020 (acceptance), SCN-3025 (rejection), and SCN-3026 (refused write). Existing
pytest/Cucumber suites remain independent regression gates.
