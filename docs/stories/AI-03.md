## Scope

CTA-owned content-hash change planning, corpus cache keys, model/configuration manifests, isolated
snapshot publication, compatibility checks, and refresh reporting. CocoIndex owns chunking,
embeddings, and index storage; CTA does not claim internal embedding counts.

## Non-goals

A CTA source-code chunker or vector store; claims about unobserved CocoIndex vector reuse; semantic
indexing of requirements/scenarios; changing M2 freshness policy.

## Normative contract notes

### Eligible corpus and change plan

The eligible corpus is exactly the `source` and `test` artifacts at the selected baseline, sorted by
artifact ID. A `ContentChangePlan` compares the eligible artifact IDs, locators, and content hashes
between the selected baseline and an optional previous baseline:

* `changed` — present in both with different content hashes;
* `added` / `removed` — present in only one;
* `unchanged` — present in both with equal content hashes.

The plan has no `items_embedded` field and makes no embedding-count claim. It records both resolved
commits (`previous_commit` and `commit`). The current manifest records its own eligible artifacts and
content hashes, and its `previous_snapshot_binding` resolves to the immutable compared manifest,
which records the previous artifact hashes. A reader can therefore follow the current manifest to
the exact previous-manifest file rather than infer the previous hashes from the new file.

### Configuration and cache identity

`RetrievalConfig` records provider, model ID/version, weights digest, runtime, formatting version,
dimension, max tokens, and the explicit `chunking_owner`/`embedding_owner = cocoindex`. A manifest
also records `config_digest = sha256(canonical config)`.

* `corpus_cache_key = sha256(repository, config_digest, sorted eligible {artifact_id, type, locator,
  content_hash})`. **Commits are excluded.**
* `snapshot_binding = snapshot:sha256(sha256(repository, commit, corpus_cache_key,
  config_digest))`. **The commit is included.**
* Two evidence-only commits with identical eligible content and identical configuration therefore
  have the same cache key but different snapshot bindings. A model/configuration change changes the
  config digest and the cache key even when content is unchanged.

### Publication

Manifests are application-owned and live outside the fixture/evaluated repository. Publication writes
an immutable `snapshots/<binding>.json` file and then atomically replaces the
`baselines/<baseline>.json` pointer. A failed refresh writes neither the pointer nor a usable
snapshot; the previous baseline pointer and its snapshot remain readable. An old snapshot file is
never rewritten by a later model change. A corrupt snapshot is not served.

### Refresh and honest reporting

`refresh(baseline, previous_baseline, config, adapter?)`:

1. Resolves the baseline and builds the plan/keys.
2. If the exact snapshot binding already exists, returns it unchanged.
3. If the previous manifest has the same config digest and cache key and the plan is empty, reuses
   the content: publishes a new manifest with the new snapshot binding, `reused=true`,
   `items_embedded=null`, `items_embedded_availability=not_available`, and no adapter call.
4. Otherwise calls the optional `IndexRefreshAdapter` (if configured). Adapter failure (or any
   exception other than a typed `RetrievalUnavailable`) is reported as
   `503 retrieval-unavailable`; no snapshot is published.
5. Publishes the manifest with measured non-negative `elapsed_ms`, `added_count`, `changed_count`,
   `removed_count`, `unchanged_count`, the snapshot binding, and the config digest.

`elapsed_ms` measures the timed phase of a **new publication**: planning, previous-manifest lookup,
cache-key construction, and adapter execution. It excludes the atomic snapshot/pointer writes and the
exact-binding cache-hit read. An exact-binding cache hit returns the existing manifest unchanged,
including its original publication `elapsed_ms` and counts; the API response does not pretend the
current request re-measured them.

`items_embedded` is reported only when the adapter exposes a non-negative counter; otherwise it is
`null` with `items_embedded_availability = "not_available"`. CTA never infers a CocoIndex embedding
count from the changed-artifact count. The default API refresh has no adapter, so it reports
`not_available`.

### Candidate combination and lifecycle-bound provenance

The existing `TraceCandidate.index_revision` remains the discovery provider's own index content
fingerprint. CTA does not rewrite that contract. AI-03 adds an explicit adaptation boundary:

* `SnapshotBoundBatch` = `{snapshot_binding, provider, provider_index_revision, model_version,
  candidates}`. The batch retains the provider's own index identity; its candidates carry the CTA
  lifecycle `snapshot_binding` in the existing `index_revision` field, which is the only identity the
  combination service may mix.
* `RetrievalLifecycle.bind(manifest, provider, artifact_id, top_k)` runs the real provider at the
  manifest baseline, verifies that the provider name matches the manifest configuration (and the
  model version when the manifest has one), verifies that the provider's candidates all report the
  provider's own index revision, and then constructs the bound batch. A mismatch is a typed
  `invalid-request` / `retrieval-unavailable` / `mixed-index-context`; it is never a silent
  provenance rewrite. The provider's original index revision is preserved in
  `provider_index_revision`.
* `CombineRequest` accepts batches plus one expected `snapshot_binding`. A batch bound to any other
  binding fails the whole combination with `409 mixed-index-context`, and no combined list is
  returned. Compatible batches are combined and re-ranked contiguously by score (descending) and
  target ID. The response's `provenance` list retains each batch's provider,
  `provider_index_revision`, and model version.
* CocoIndex's internal index identity remains unavailable when the MCP contract does not expose it;
  the CTA snapshot binding is explicitly a CTA binding, not a fabricated CocoIndex identity.
* Combination never writes a link, evidence, or finding.

### API

|Endpoint|Behaviour|
|---|---|
|`POST /api/retrieval/refresh`|`{baseline, previous_baseline?, config?}` → published `RetrievalManifest`; default config reports backend identity/counts as `not_available`.|
|`GET /api/retrieval/manifests`|All published manifests.|
|`GET /api/retrieval/manifests/{baseline}`|Current manifest for the baseline or `404 retrieval-snapshot-not-found`.|
|`POST /api/retrieval/combine`|`{snapshot_binding, batches: [SnapshotBoundBatch]}` → combined candidates + batch provenance or `409 mixed-index-context`.|

The snapshot directory is `CTA_RETRIEVAL_SNAPSHOT_DIR` (default `<repo_root>/.cta/retrieval-snapshots`)
and must resolve outside `fixtures/` and the evaluated repository.

### CocoIndex boundary

CTA owns the manifest and the content-addressed cache key. CocoIndex owns code chunking, embeddings,
its internal incremental index, and any vector store. The manifest records the configured model
identity when known; `not_available` is preferred to a fabricated value. A published CTA snapshot
does not claim that CocoIndex embedded any particular number of items or retained any particular
vector.

## Verification plan

Hand-labeled baseline change sets; evidence-only commits with both commit-bound manifests; a
model/configuration change that invalidates the cache while the old manifest remains readable; a
failed publication that leaves the previous pointer usable; mixed-binding rejection and compatible
combination through the real combination service/API, preserving provider provenance; and refresh
cost separating measured elapsed time and artifact counts from `not_available` embedding data.
An exact-binding cache hit is observed returning the existing manifest (original publication
timing/counts), not a re-measured publication. Deterministic adapters make the criteria model-free.
Evidence is recorded in `docs/reports/closeout/`.

## Contract impact

Additive retrieval lifecycle models (`RetrievalConfig`, `RetrievalManifest`,
`ContentChangePlan`, `SnapshotBoundBatch`, `BatchProvenance`) and endpoints; MINOR schema bump
`0.7.0 → 0.8.0`. `TraceCandidate` is unchanged: its `index_revision` remains the provider's own
identity, and the lifecycle binding is carried by the explicit batch adaptation. No change to
`TraceLink`, evidence, findings, or the M2 freshness policy.
